# Atoms Demo · 实现说明

> 配套提交材料。对应的 Demo 地址与源码地址见笔试文档第 4 节。

## 一、实现思路与关键取舍

### 1. 先锁定"最小可信闭环"，再谈功能量

题目要求的是一个"具备类似 Atoms 能力与 UI 交互体验"的可运行应用。这类需求最容易失焦的地方是把它做成一个功能清单。所以我先把要证明的事情压缩成一句话：

**一句话需求 → Agent 生成代码 → 右侧立刻能点着用 → 操作产生的数据存得下来 → 能继续改、能分享出去。**

其余一切（主题、模板、更多 Agent、集成）都是加分项，不进入第一版。产品骨架对齐参考产品 Atoms：工作区 → 项目对话 → App Viewer（桌面/手机）→ 版本 → 发布公开链接；Agent 也采用"有名字的团队"这一形态（Emma 产品经理 / Bob 架构师 / Alex 工程师 / Ada 质检），因为这是 Atoms 最有辨识度的交互隐喻。

### 2. 四个关键取舍

**取舍一：产物统一为单文件 HTML，而不是让模型自由生成工程。**
让模型生成 React 多文件项目，会立刻引入依赖安装、构建、路径、版本漂移等一堆和 Demo 目标无关的失败面，而且在沙箱里预览的成本极高。收敛成"单文件 HTML（内联 CSS/JS、禁止外链资源）"后，预览就是 iframe 渲染、持久化就是存一个字符串、分享就是把它吐出来、导出就是一个能双击运行的文件 —— 一个决定解决了四件事。代价是不支持多页面与复杂状态，这对本 Demo 的规模是划算的。

**取舍二：让生成物自带一个数据层，这是本 Demo 与"套壳聊天生成器"的分界线。**
大多数同类 Demo 生成的是一张静态页面，一刷新就回到原样。这里在渲染前向产物注入一段运行时 SDK，生成物调用 `window.atoms.store('集合名')` 就能读写真正的服务端存储：

```
生成物（sandbox iframe，独立源）
  └─ window.atoms.store('巡检记录').insert({...})
       └─ postMessage ──► 宿主 bridge.js（校验来源）
            └─ POST /api/data ──► SQLite / Upstash Redis
```

于是"AI 生成的应用"第一次能承载真实业务数据：刷新不丢、换设备打开还在、分享出去的链接用的是同一份数据。同时 SDK 带 5 秒超时并降级到 localStorage，因此**导出的单文件应用脱离平台也能独立运行**。

**取舍三：隔离优先于便利。**
生成物是"用户提交的任意 HTML"，绝不能挂在主站源下渲染。编辑器预览和发布页统一使用 `sandbox="allow-scripts allow-forms allow-modals allow-popups allow-downloads"`（**不给 `allow-same-origin`**），桥接层再校验消息必须来自自己的舞台 iframe。代价是宿主与生成物之间只能用 postMessage 通信，换来的是不存在 XSS 后门。

**取舍四：零第三方依赖。**
HTTP 用 `node:http`，存储用 Node 24 内置的 `node:sqlite`（云端切纯 HTTP 的 Upstash REST），模型调用用内置 `fetch`，`.env` 自己解析。收益是 `git clone` 之后一句 `node server.js` 就能跑，没有 `node_modules`、没有构建步骤、没有供应链风险，而且整份代码可以逐行读完。代价是少了框架的便利，需要自己写路由和状态管理 —— 对这个体量来说，控制力比便利更重要。

另外做了一个"防翻车"设计：**双模式 Agent**。没有配置 API Key 时自动进入 Mock 模式，内置生成器按需求关键词选择业务模板（巡检 / 任务 / 记账 / 客户 / 库存 / 通用台账），拼出一个**真实可交互、真实调用数据层**的应用，事件流与真实模型完全一致。目的是保证任何人点开链接都能走完整主流程，而不是看到一张截图。

**取舍五：兜底必须诚实。**
Mock 模式第一版只认得「数据台账」这一类需求，其他需求全部掉进通用台账兜底 —— 结果就是有人输入"做一个射击游戏"，它却一本正经地生成了一份"通用数据台账"，还在方案里写"识别到这是一个录入+查看+维护型应用"。这比直接说"我不会"更糟：它消耗了用户的信任。

现在的策略分三层：**能做的做好，不能做的说清楚**。

1. 把 Mock 的覆盖面从「数据台账」扩到三类：数据台账、小游戏（射击打靶，含成绩入库与历史排行）、展示型站点（官网/落地页，含预约留言写库）；
2. 明确超出能力范围的需求（视频、文档、音频、原生 App、聊天机器人）不再硬编产物，而是返回一条诚实的说明，并在对话里给出「去配置模型」按钮；
3. 连通用台账兜底的文案也改掉了 —— 现在会说"没有识别到具体业务类型，先按通用台账生成骨架，你可以直接说把字段改成 A/B/C"，而不是假装自己听懂了。

### 模型接入方式（两种，都已实现）

1. **界面内配置**（推荐）：工作台左下角「模型设置」→ 选服务商预设（DeepSeek / Kimi / 硅基流动 / 智谱 / 通义千问 / OpenAI，一键填好地址与模型名）→ 粘贴 Key → 「测试连接」→「保存」。配置写进数据库，重启与重新部署都不丢；Key 只存服务端，读取接口只返回掩码。
2. **环境变量**：`.env` 里配置 `LLM_BASE_URL / LLM_API_KEY / LLM_MODEL`。优先级：请求临时覆盖 > 界面配置 > 环境变量 > 默认值。

两种方式都不配也能跑（Mock 模式）。配好之后用 `node tools/test-live.mjs` 做全链路验收。

### 暂未完成

- **账号体系很轻**：注册只校验邮箱格式与密码长度，没有邮箱验证、找回密码、第三方登录；会话是 30 天 httpOnly Cookie，没有刷新机制与吊销列表；也没有做项目级协作权限（目前是「自己的项目只有自己能改，已发布的谁都能看」）。
- **`/api/data` 没有限流与配额**：生成物可以无限制写入。
- **界面配置的 Key 是全局共享的**：虽然现在有了账号，但模型配置是平台级的，任何注册用户都能替换或消耗这份 Key；正式产品需要把 Key 收敛到账号级并配合配额。
- **Mock 模式仍然是关键词匹配**：目前覆盖数据台账、小游戏、展示型站点三类，三类之外（例如"做一个抽奖转盘""做一个数据看板"）会落到通用台账，或走"如实告知"分支；真正的任意需求理解只能由配置模型提供。另外小游戏只有打靶一种，说"贪吃蛇"也会产出打靶游戏，只是标题如实标注。
- **静态质检不是 AST 级校验**：Ada 的检查是规则式的（结构完整性、外链引用、是否调用数据层），不能发现语法错误；运行时报错触发的自动修复在 Mock 模式下不生效。
- **生成物的能力边界**：单文件形态不支持多页面、复杂状态管理和需要 npm 生态的应用；也没有做移动端原生体验。
- **多模态输入**：还不支持上传截图/设计稿作为生成参考。

### 验证方式

不是"看代码觉得应该没问题"，而是逐条跑过：

- 生成器单独有测试：`node tools/test-mock.mjs` 覆盖 10 类需求（游戏 / 站点 / 数据台账 / 完全不认识的描述 / 视频 / 文档 / 原生 App），校验落到的产物形态是否符合预期、产物能否通过质检规则；

- 后端主链路用 `node tools/smoke.mjs` 覆盖（工作区 → 建项目 → SSE 流式生成 → 渲染注入 → 数据读写 → 发布 → 分享页 → 404 兜底 → 二次迭代）；
- 界面部分在真实浏览器里完整点过一遍：建工作区 → 生成 → 在生成的应用里写入数据 → 数据面板核对 → 发布 → 新标签页打开公开链接确认数据一致 → 继续对话迭代 → 版本回滚。

过程中发现并修复的三个真实缺陷（都属于"只看代码发现不了"的类型）：

1. 运行时 SDK 原本注入在 `</body>` 前，而生成物自己的脚本更早执行，导致 `window.atoms` 尚未定义就调用、脚本中断，界面表现是"页面渲染出来了但数据一直加载中"；
2. 发布页没有把舞台 iframe 注册给桥接层，来源校验失败，分享出去的应用读不到数据；
3. Mock 模式下二次迭代会丢掉上一版的应用类型（说"加个筛选框"却得到一个完全不同的应用），现已改为沿用上一版模板并保留已有特性（深色主题、筛选器）。

## 三、数据持久化与基本使用流程

### 数据持久化：两层，同一套接口

| 层 | 存什么 | 本地 / 容器 | 免费托管 |
| --- | --- | --- | --- |
| 平台数据 | 账号与会话、工作区、项目、对话消息、版本（含完整应用源码）、模型配置 | `node:sqlite` 单文件 | Upstash Redis REST |
| 生成物的业务数据 | 生成的应用通过 `atoms.store` 写入的记录，按 `(项目, 集合, 记录ID)` 存储 | 同上 | 同上 |

实现要点：

- 两个驱动（`src/store.js`）实现同一组异步方法，`STORAGE` 环境变量切换，业务代码不感知；
- 生成物写数据走 `window.atoms.store()` → postMessage → 宿主 host bridge → `POST /api/data` → 数据库，生成物本身不接触数据库连接，也拿不到主站凭据；
- SDK 带 5 秒超时，宿主不可用时自动降级到 `localStorage`，所以**导出的单文件应用脱离平台依然可用**；
- 数据不随复刻复制：复刻的是应用与数据结构，业务数据从零开始 —— 这是刻意的选择，避免把别人的真实数据复制走。

怎么验证：在预览里新增几条记录 → 刷新页面 → 数据还在；切到「数据」页签可以看到服务端这张表的真实内容；发布后把链接发给别人，对方看到的是同一份数据。

### 基本使用流程（完整覆盖）

1. **初始化**：注册时自动创建工作区（`workspace_id`），项目、数据、配置全部挂在它下面；
2. **注册 / 登录**：邮箱 + 密码注册，scrypt 加盐哈希入库；登录后下发 httpOnly Cookie 会话（30 天）；支持退出、改名；不想注册可以走「一键体验」游客账号；
3. **核心主流程**：一句话需求 → Agent 团队（方案 → 生成 → 质检）→ App Viewer 立刻可交互 → 数据实时落库 → 继续对话迭代出 v2/v3 → 版本历史回滚 → 发布成公开链接 → 别人可以复刻。

## 四、延展与衍生能力

### 本期已经实现的（都属于主流程之外的衍生能力）

| 能力 | 说明 | 为什么算衍生能力 |
| --- | --- | --- |
| 复刻 Remix | 从分享页把自己或别人的应用复制到自己的账号继续改 | 让"生成结果"变成可流通的资产，形成内容飞轮 |
| 版本历史与回滚 | 每次生成/修改都留版本，可对比预览、一键回退 | 把一次性的生成变成可迭代的工程过程 |
| 导出独立单文件 | 导出后双击即可运行，自动降级到 localStorage | 产物脱离平台存在，降低锁定风险 |
| 发布与分享 | 自定义地址、发布前检查清单、公开链接、下线 | 从"能用"走到"能给别人用" |
| 运行时自检与自动修复 | 生成物在浏览器里抛错会回传宿主，触发质检 Agent 二次修复并产出新版本 | 让"自检"成为闭环，而不是生成完就结束 |
| 数据面板 | 查看/删除生成物写入的真实记录，按集合分组 | 让生成物的数据可见、可管理，而不是黑盒 |
| 模型自带（BYO Key） | 界面内配置任意 OpenAI 兼容接口并测试连通性 | 把模型选择权交给用户，便于私有化与成本控制 |

### 如果继续做，我建议再补的衍生能力（按优先级）

1. **数据导入 / 导出（CSV）**：把生成物里的记录导出成表格、支持批量导入。成本很低，但立刻把"玩具"变成"能接现有工作流"的工具。
2. **定时任务与通知**：让生成的应用能"主动干事"（到期提醒、库存预警、每日汇总），这是从"记录工具"跨到"业务系统"的关键一步。
3. **多页面与数据关联**：主从表、列表→详情的路由，突破单文件单页面的天花板。
4. **团队协作**：项目共享、评论、变更对比（diff）、发布审批，对应真实团队的使用方式。
5. **接入真实数据源**：数据库连接器（Supabase / Neon）与第三方 API，让生成物读写真实业务系统。
6. **应用市场**：把复刻做深 —— 公开作品广场、按场景分类、一键基于模板再创作。

判断顺序的逻辑：先让产物可用（导入导出、通知），再让它能承载复杂业务（多页面、数据源），最后才是平台化（协作、市场）。

## 五、如果继续投入时间：扩展方向与优先级

**P0 · 先补齐"可用性"的地基（0.5–1 天）**

1. **真实鉴权与项目权限**：工作区账号 + 项目级读写权限 + 分享链接的只读模式；这是从 Demo 走向可交付的第一道门。
2. **`/api/data` 限流与配额**：按项目限制写入频率与总量，并对生成物的数据形状做白名单校验。
3. **质量兜底升级**：把 Ada 的静态检查换成真正的语法解析 + 无头浏览器渲染校验（截图对比 + 控制台错误采集），让"自检"从规则式变成可验证式。

**P1 · 把"生成质量"拉成真正的生产力（1–2 天）**

4. **多智能体可观测**：把每次生成的过程、耗时、Token、失败原因沉淀成可回看的执行日志，支持单步重跑。
5. **生成物能力增强**：内置常用组件（图表、日历、看板）作为可复用渲染片段，减少模型自由发挥带来的不稳定；支持多页面路由与数据关联（主从表）。
6. **多模态输入**：支持上传截图/设计稿 + 参考站点，让"照着这个做"成为主入口。

**P2 · 平台化（按需）**

7. **数据源与集成**：接入真实数据库（Supabase/Neon）、第三方 API 密钥托管，让生成物能连真实业务系统。
8. **协作与审核**：项目共享、评论、变更对比（版本 diff）、发布审批流。
9. **自定义域名与 SEO/埋点**：把发布能力从"给个链接"推进到"能给业务用"。

优先级判断依据很简单：**先解决"能不能被别人放心用"（权限、限流、可观测），再解决"生成得好不好"（组件库、多模态），最后才是平台化。** 当前版本在"体验与形态"上已经能说明问题，剩下的瓶颈全在可运营性上。
